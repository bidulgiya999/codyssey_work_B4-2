말할 문장:

Linux 프로그램에서 발생하는 메모리 문제, CPU 과점유, 교착상태를 분석했습니다. 로그와 관제 데이터를 수집하고 환경변수 변경 전후를 비교해 보고서로 정리했습니다. 절차와 코드·보고서 정리에는 Codex의 도움을 받았고, 제가 직접 Ubuntu에서 명령을 실행하며 실제 출력을 확인했습니다.

3. 관제: 무엇을 어떻게 기록했나요?

열 파일: monitor.sh
https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/scripts/monitor.sh. 가리킬 부분: ps 조회, awk 추출, 반복문, sleep 1.

말할 문장:

부모 실행기와 실제 작업 자식 PID를 구분했습니다. monitor.sh는 지정한 PID를 약 1초마다 ps로 조회하고 시간, CPU, 메모리, 스레드 수와 상태를 CSV로 기록합니다. CPU의 짧은 변화는 top을 0.1초 간격으로 추가 기록했습니다.

코드와 출력 해설:

ps -p "$pid" -o pid=,ppid=,etimes=,pcpu=,pmem=,rss=,nlwp=,stat=

- -p: 해당 PID만 조회합니다. -o: 필요한 출력 항목을 고릅니다. 각 항목의 =는 제목을 생략합니다.
- PID는 프로세스 번호, PPID는 부모 프로세스 번호입니다.
- etimes는 실행 경과 초, pcpu는 실행 시간에 걸친 평균 CPU 사용률, pmem은 메모리 비율입니다.
- RSS는 현재 실제 메모리에 상주하는 양이며 단위는 KiB입니다. 메모리 증가 비교에는 이 값을 사용했습니다.
- NLWP는 스레드 수, STAT는 상태입니다. S는 대기, R은 실행 중 또는 실행 가능, N은 낮은 우선순위, l은 여러 스레드, +는 전경 프로세스 그룹을 뜻합니다.
- awk는 공백으로 구분된 필드를 골라 쉼표로 연결합니다. Z로 시작하는 좀비 상태는 관제 대상에서 제외합니다.
- date는 측정 시간을 붙입니다. sleep 1은 다음 조회 전 1초를 쉽니다. 명령 수행 시간도 있으므로 정확히 1초 간격을 보장하지는 않습니다.
- CSV는 첫 줄이 항목 이름이고 이후 한 줄이 한 번의 관측입니다. 로그와 같은 시간대인지 확인하며 읽습니다.

추가 질문: top 명령의 옵션은 무엇인가요?

LC_ALL=C top -b -d 0.1 -w 180 -p "$TOP_PIDS"

답변: LC_ALL=C는 출력 형식을 일정하게 하고, -b는 파일 저장용 배치 출력, -d 0.1은 갱신 간격, -w 180은 출력 폭, -p는 관측할 PID 목록입니다. 이 실행에는 횟수 제한을 두지 않아 앱 종료 뒤에도 top을 별도로 정리했습니다. 분석에서는 첫 화면을 제외했습니다.

쉬운 설명: ps는 사진 한 장, 반복 관제는 사진을 시간순으로 모은 기록입니다. top은 짧은 구간의 변화까지 보는 데 사용했습니다. htop과 pstree는 다른 선택지이며 이번에 실제 사용한 도구와 구분해서 설명합니다.

4. OOM: 메모리가 왜 증가하다 종료됐나요?

열 파일: OOM 보고서
https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/01-oom.md.

가리킬 순서: Before & After 표 → 작업 PID의 CSV 발췌 → 종료 로그 → 조치 및 검증.

말할 문장:

메모리 한도를 128MB에서 256MB로 바꾸고 CPU 설정 100과 동시 설정 false는 유지했습니다. RSS와 앱의 Heap 로그가 증가했고, Memory limit exceeded와 Self-terminating process 로그를 근거로 앱의 MemoryGuard 보호 종료로 판단했습니다. 생존 시간은 약 17.185초에서 32.355초로 늘었지만 같은 종료가 반복됐으므로 임시 조치입니다.

출력 읽기:

- Before 작업 PID 11373: RSS 18,392 → 최대 146,412KiB. Heap 150MB에서 150MB >= 128MB를 기록했습니다.
- After 작업 PID 11834: RSS 18,452 → 최대 274,492KiB. Heap 275MB에서 275MB >= 256MB를 기록했습니다.
- Heap은 앱이 출력한 값이고 RSS는 OS가 관측한 값이므로 동일한 값일 필요가 없습니다.
- Heap이 약 3초마다 25MB씩 증가해 계단 모양의 증가 추세가 나타났습니다. 한도는 단계 사이에 있어 128이나 256과 정확히 같은 값에서 멈추지 않았습니다.
- 두 실행의 종료 코드는 137입니다. 이는 SIGKILL과 부합하는 보조 정보이며, 이것만으로 누가 왜 종료했는지는 알 수 없습니다. 종료 이유는 앱 로그와 함께 판단합니다.
- After 마지막 RSS 0 한 줄은 종료 경계에서 관측됐습니다. 메모리 누수가 정상 복구됐다는 증거로 해석하지 않았습니다.
- 생존 시간은 앱의 listening 로그에서 MemoryGuard 종료 요청 로그까지 계산했습니다. 폴더 생성 시각으로 계산하지 않았습니다.

질문: Windows 메모리 사용률이 높아서 종료된 것 아닌가요?

답변: 이번 자료에서는 앱이 정한 한도 초과와 자체 종료 로그를 확인했습니다. Windows 전체 메모리 비율과 앱 한도는 다른 지표입니다. 커널 OOM Killer가 종료했다고 확정할 근거로 사용하지 않았습니다.

질문: 왜 한도 증가가 근본 해결이 아닌가요?

답변: 메모리가 증가하는 코드를 수정하지 않고 종료 판단 한도만 높였기 때문입니다. 더 큰 컵으로 바꿔 넘치는 시간을 늦춘 것과 같습니다. 정확한 누수 코드 위치는 이번 증거만으로 확인하지 못했습니다.

질문: 근본적으로 무엇을 고치겠나요?

답변: 소스를 수정할 수 있다면 계속 쌓이는 참조와 캐시를 조사하고, 필요 없는 데이터 해제와 캐시 크기 제한 등을 적용한 뒤 같은 부하에서 메모리 추세를 검증하겠습니다. 이는 추가 제안이며 이번에 수정한 내용은 아닙니다.

참조: 보고서 안의 두 실행 settings.txt, monitor-11373.csv, monitor-11834.csv, app.log, exit-code.txt 링크를 엽니다. settings는 의도한 설정, 부팅 로그는 앱이 읽은 설정, CSV는 자원 추세, app.log는 종료 판단의 근거입니다.

5. CPU: 왜 보호 종료라고 판단했나요?

열 파일: CPU 보고서
https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/02-cpu.md.

가리킬 순서: 비교 표 → Watchdog 로그 → 냉각과 ELAPSED 86 → top 70% 화면 → 수동 정리 기록.

말할 문장:

메모리 설정 512와 동시 설정 false를 유지하고 CPU 설정만 80에서 40으로 바꿨습니다. 80 설정에서는 앱 내부 부하 50.5%에서 임계치 위반과 Watchdog의 SIGTERM 종료 요청이 기록됐습니다. 40 설정에서는 냉각 동작과 86초 시점의 생존 및 작업 진행을 확인했습니다. 다만 top 최대는 70%였으므로 프로세스 전체 CPU가 40% 이하로 제한됐다고 설명하지 않았습니다. 변경 후 마지막 종료는 제가 수동으로 정리한 것입니다.

왜 이 설정인가요?

- 메모리 512는 제공 범위 안에서 메모리 한도를 높인 비교 조건입니다. 시스템 RAM 자체를 늘리거나 메모리 문제를 수정한 것은 아닙니다.
- false는 교착 재현 조건을 끈 상태입니다. 두 CPU 실행에서 같은 조건을 유지했습니다.
- 80은 보호 종료를 관찰한 조건, 40은 냉각 동작과 생존 변화를 비교한 조건입니다. 실제 앱 동작은 로그로 확인하며, 변수 이름만 보고 종료 기준을 추정하지 않습니다.

출력 읽기:

- Before 작업 PID 12479: 19:42:29.310 시작, 19:43:05.695 임계치 위반. 로그 기준 약 36.385초입니다.
- CPU Threshold Violated! (50.5%)와 WATCHDOG ... (SIGTERM)은 보호 정책이 종료를 요청한 근거입니다. 설정이 80인데 50.5에서 종료됐으므로 “80을 넘겨 종료됐다”라고 말하면 실제 로그와 다릅니다. 정확한 내부 판단식은 확인하지 못했습니다.
- After 작업 PID 13127: 앱 내부 부하 40%에서 cooldown을 시작했고 ELAPSED 86인 시점에도 진행했습니다. 이 수치는 관측 구간의 생존 근거입니다.
- top은 Before 최대 50%, After 최대 70%입니다. 19:47:16 화면에서 70%가 관측됐고, 앱은 같은 초에 Current Load 39.53%를 기록했습니다.
- 두 값은 같은 지표가 아닙니다. top은 프로세스 전체의 측정 구간 CPU 사용률이고 Current Load는 앱이 기록한 내부 값입니다. 메모리 작업도 같은 시각에 기록됐지만 70%의 정확한 원인이라고 확정하지 않았습니다.
- 두 실행의 관측 길이도 다르므로 최대값만으로 전체 성능이 개선됐다고 평가하지 않았습니다.

질문: ps의 낮은 CPU와 top의 70% 중 무엇이 맞나요?

답변: ps의 pcpu는 실행 시간에 걸친 평균, top은 갱신 구간 사용률입니다. 측정 구간이 달라 동시에 다른 값이 나올 수 있습니다.

질문: 둘 다 종료 코드 143인데 같은 장애인가요?

답변: 143은 SIGTERM 종료와 부합하지만 요청자를 알려주지는 않습니다. Before는 Watchdog 로그, After는 19:48:26의 manual SIGTERM 정리 기록으로 구분했습니다.

질문: 응답 지연도 개선됐나요?

답변: 요청 응답 시간이나 P99 지연은 측정하지 않았습니다. 냉각과 관측 구간의 생존·진행만 확인했다고 설명합니다.

쉬운 설명: CPU_MAX_OCCUPY는 앱에 전달하는 설정입니다. OS가 모든 실행 흐름을 합쳐 재는 CPU 수치에 강제 상한을 거는 기능이라고 단정할 수 없습니다. Watchdog는 보호 감시 장치, SIGTERM은 종료 요청입니다.

참조: 보고서의 app.log, ps-check.txt, top-summary.txt, top-high-frames.txt, top-high-app-context.txt, cleanup.log 링크를 엽니다. 요약 수치가 궁금하면 top 원본 화면을 함께 보여줍니다.

6. Deadlock: 살아 있는데 왜 멈췄다고 하나요?

열 파일: Deadlock 보고서
https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/03-deadlock.md.

가리킬 순서: 비교 표 → 두 스냅샷 → LOCK ACQUIRED와 WAITING → false 변경 후 진행 로그.

말할 문장:

메모리 512와 CPU 40은 유지하고 동시 설정만 true에서 false로 바꿨습니다. true에서는 PID가 살아 있지만 10초 사이 RSS와 로그 크기가 그대로였고 스레드들이 대기했습니다. 첫 워커는 A를 가진 채 B를, 두 번째 워커는 B를 가진 채 A를 기다리는 로그가 있어 순환 대기로 판단했습니다. false에서는 10초 사이 로그가 661바이트 증가하고 작업이 진행해 관측 구간에서 해당 교착 경로가 회피됐다고 판단했습니다.

출력 읽기:

- true의 작업 PID는 15052입니다. 19:53:43과 19:53:53의 RSS는 모두 18,428KiB, 로그 크기는 모두 2,802바이트였습니다. 마지막 로그 시각도 멈춰 있었습니다.
- ps -ef는 PID 존재를, ps -L은 스레드 상태를, 반복 CSV와 스냅샷은 변화 여부를 확인하는 근거입니다. 로그 크기·수정 시각은 stat으로 확인했습니다.
- futex_do_wait는 동기화 대기 지점입니다. 정상적인 대기에도 나타나므로 이 값 하나로 교착을 확정하지 않았습니다.
- 로그에는 Worker-Thread-1이 Shared_Memory_A를 획득한 뒤 Socket_Pool_B를 기다리고, Worker-Thread-2는 B를 획득한 뒤 A를 기다립니다. 자원 소유와 요청 방향을 함께 읽어 순환 관계를 찾았습니다.
- false의 작업 PID는 16896입니다. 19:58:58에서 19:59:08 사이 로그가 8,778 → 9,439바이트로 증가했고 메모리 정리와 CPU 작업 로그가 이어졌습니다.
- RSS 감소만으로 정상이라고 판단하지 않았습니다. 실제 작업 로그가 계속 진행하는지도 확인했습니다.

질문: 교착의 네 조건은 무엇인가요?

답변:

1. 상호 배제: 한 자원을 한 번에 하나의 워커만 사용합니다.
2. 점유 대기: A 또는 B를 가진 채 다른 자원을 기다립니다.
3. 비선점: 락을 외부에서 강제로 빼앗기보다 소유자가 반환해야 하는 구조입니다. 이번에는 소유자가 반환하지 않고 기다리는 로그를 근거로 설명합니다.
4. 순환 대기: 첫 워커 → B → 두 번째 워커 → A → 첫 워커의 고리가 생깁니다.

쉬운 설명: 각자 열쇠 하나를 쥐고 상대 열쇠를 기다려 아무도 다음 작업을 못 하는 상황입니다. 네 조건을 외우는 데 그치지 않고 이번 로그의 소유·대기 관계에 연결합니다.

질문: false면 스레드가 한 개만 있나요?

답변: 아닙니다. false에서도 세 스레드가 관측됐습니다. 이 앱의 특정 동시 처리 경로를 바꾼 결과이며 프로그램 전체가 단일 스레드라는 뜻은 아닙니다.

질문: 스레드별 RSS를 더하면 전체 메모리인가요?

답변: 스레드는 프로세스 주소 공간을 공유하므로 반복 표시된 RSS를 단순 합산하면 안 됩니다.

질문: 143은 교착이 스스로 해결됐다는 뜻인가요?

답변: 아닙니다. 재현 증거를 모은 뒤 수동 SIGTERM으로 정리했습니다. 두 실행 모두 cleanup.log로 장애 상태와 실험 종료를 구분했습니다. PID 조회에 제목만 남고 포트 조회가 비어 대상 프로세스와 해당 listening 소켓이 정리됐음을 확인했습니다.

참조: 보고서의 두 실행 snapshot-1.txt, snapshot-2.txt, 작업 PID의 CSV, app.log, cleanup.log를 엽니다. PID 존재 → 시간에 따른 정체 → 스레드 대기 → 로그의 순환 관계 순서로 설명합니다. 특정 TID가 Worker-Thread-1 또는 2인지까지는 확정하지 않았습니다.

7. 운영 응용 질문: 왜 그렇게 판단했나요?

질문: monitor.sh로 장애를 더 일찍 탐지하려면요?

답변: 실제 시간 차이에 따른 RSS 증가율, 여러 구간의 지속 상승, 한도 접근을 함께 감시하고 알림을 추가하겠습니다. 시작 직후 증가나 정상 캐시를 누수로 오인하지 않도록 지속 시간과 작업 진행도도 보겠습니다. PID 재사용 구분, 로그 회전과 수집 오류 처리도 필요합니다. 이번 스크립트는 기록용이며 이 개선을 구현한 것은 아닙니다.

질문: 세 장애 중 무엇이 가장 치명적인가요?

답변: 서비스 영향에 따라 다릅니다. 교착이 핵심 요청 경로에서 조용히 계속된다면 프로세스 생존 감시만으로 놓칠 수 있어 치명적입니다. 반대로 호스트 메모리 고갈이 임박했다면 다른 서비스까지 영향을 주는 OOM이 더 긴급합니다. 조건과 영향 범위를 먼저 말하겠습니다.

질문: OOM과 교착이 동시에 발생하면요?

답변: 빠르게 로그·PID·메모리와 스레드 상태를 보존하면서 서비스 영향을 확인합니다. 호스트 메모리 고갈이 임박했다면 해당 소비를 제한하거나 격리해 확산을 막는 것을 우선합니다. 메모리는 안정적이고 핵심 기능만 교착됐다면 그 경로 복구를 우선할 수 있습니다. 증거를 무한히 모으느라 복구를 지연하지 않겠습니다.

질문: 소스 코드를 수정할 수 있다면요?

답변: 메모리는 불필요한 참조와 무제한 캐시를 조사하고 크기 제한·수명 관리를 적용하겠습니다. CPU는 프로파일링으로 병목을 찾고 바쁜 대기, 비효율 계산, 무제한 작업 큐를 개선하겠습니다. 교착은 락 획득 순서를 통일하고 예외 시 해제를 보장하겠습니다. 타임아웃을 넣을 때도 이미 획득한 자원 정리와 재시도 정책이 필요합니다. 수정 뒤에는 기능과 작업 진행도까지 재검증해야 합니다.

질문: 다시 수행한다면 무엇을 바꾸겠나요?

답변: 부하와 관측 시간을 맞추고 설정·버전·PID 시작 시각·측정 간격을 함께 기록하겠습니다. 메모리 단위와 CPU 측정 구간을 처음부터 구분하고, PID 생존 외에 실제 응답과 작업 진행도도 측정하겠습니다. 예상과 다른 top 70% 같은 결과도 그대로 보존하겠습니다.

질문: 스케줄링 보너스도 확정할 수 있나요?

답변: 이번 로그는 A 완료 후 B, B 완료 후 C가 시작하는 앱 작업 순서여서 FCFS와 유사한 순차 처리로 설명할 수 있습니다. 이것만으로 Linux 커널의 CPU 스케줄링 알고리즘을 확정할 수는 없습니다. 보너스이며 필수 세 장애 결과와 구분합니다.
