# 평가 직전 설명 연습

이번 실습일은2026-11-10입니다. [전체 결과](README.md)에서 보고서와 증거로 이동합니다. 명령어와 보고서 정리에 Codex의 도움을 받았고, 사용자가 Ubuntu에서 직접 실행하며 실제 출력을 확인했습니다. 모르는 내부 구현은 확인하지 못했다고 설명합니다.

## 1. 발표 순서

과제 목적 → 환경과 관제 → OOM → CPU → Deadlock → 조치 효과와 한계 순서로 설명합니다. 각 보고서는 현상 → 증거 → 원인 판단 → 조치 → 검증 순서입니다.

## 2. OOM: 약 1분 설명

열 화면: [OOM 보고서](reports/01-oom.md)의 비교 표와 종료 로그.

> 앱 실행 후 메모리 사용량이 증가하다 종료됐습니다. 메모리 한도를128에서256MB로 바꾸고 CPU100과 동시 설정false는 유지했습니다. RSS 증가를 관제했고, Memory limit exceeded와 Self-terminating 로그로 앱의 MemoryGuard 보호 종료를 판단했습니다. 생존 시간은17.185초에서32.355초로 늘었지만 같은 종료가 반복됐으므로 한도 상향은 임시 조치였습니다.

숫자는 표를 보며 읽어도 됩니다. “메모리 증가 → 한도 초과 → 보호 종료 → 한도 상향으로 지연”이라는 연결을 설명하는 것이 핵심입니다.

## 3. CPU: 약 1분 설명

열 화면: [CPU 보고서](reports/02-cpu.md)의 비교 표, Watchdog 로그와70% 화면.

> CPU 설정80에서는 앱 내부 부하 상승 후 Watchdog가 SIGTERM을 요청했습니다. 설정40으로 바꾼 뒤에는 냉각과86초 시점의 생존·진행을 확인했습니다. 다만 top의 프로세스 전체 구간 최대는70%였습니다. 앱 설정과 내부 부하, OS 측정은 구분해야 하므로 CPU 전체가40% 이하로 제한됐다고 설명하지 않았습니다. 변경 후 마지막 종료는 수동 정리입니다.

70%는 지우거나40%로 바꾸지 않습니다. 예상과 다른 결과를 원본 화면으로 대조하고 관측 범위에 맞춰 설명한 사례입니다.

## 4. Deadlock: 약 1분 설명

열 화면: [Deadlock 보고서](reports/03-deadlock.md)의 비교 표와 자원 보유·대기 로그.

> true에서는 PID가 살아 있었지만10초 간격 두 관측에서 RSS와 로그가 그대로였습니다. 첫 워커는 A를 가진 채 B를, 두 번째는 B를 가진 채 A를 기다려 순환 대기를 이뤘습니다. 동시 설정만false로 바꾸자 같은10초 비교에서 로그가661바이트 늘고 작업이 진행했습니다. 그래서 관측 구간에서 해당 교착 경로가 회피됐다고 판단했습니다.

“PID 존재 = 정상 진행”은 아닙니다. futex 대기는 정상 상황에서도 가능하므로 자원 관계와 로그 정체를 함께 확인했습니다.

## 5. 질문받으면 답할 핵심

| 질문 | 답변의 핵심 |
|---|---|
| 왜 다른 설정을 유지했나요? | 변경 변수의 영향을 비교하기 위해서입니다. |
| RSS가 무엇인가요? | OS가 관측한 실제 RAM 상주량입니다. 앱 내부Heap과 다릅니다. |
| 왜150/275MB에서 종료됐나요? | 앱 값이25MB 단위로 증가해128/256을 넘은 다음 단계에서 관측됐습니다. |
| 137이면 커널OOM인가요? | 숫자만으로 주체를 알 수 없습니다. 이번에는MemoryGuard 로그로 판단했습니다. |
| 143이면 모두Watchdog인가요? | 수동SIGTERM도143일 수 있습니다. 종료 로그와cleanup.log를 대조합니다. |
| 설정40인데 왜top70인가요? | 앱 설정·내부값과 프로세스 전체 구간 측정은 다릅니다. 정확한 작업별 기여도는 미확인입니다. |
| false면 스레드가 하나인가요? | 실제3개가 관측됐으므로 전체 단일 스레드 전환으로 해석하지 않았습니다. |
| 정확한 누수 코드 위치는요? | 바이너리 내부는 분석하지 않았고, 이번 증거로는 특정 코드 위치를 확정하지 않았습니다. |

## 6. 남은 시간에 연습하는 방법

1. OOM 비교 표·종료 로그를 열고 위 설명을 본인 말로 두 번 말합니다.
2. CPU에서는 “냉각·생존 확인”과 “OS 최대 감소 미확인”을 구분해 말합니다.
3. Deadlock에서는 A와B를 종이에 그리고 두 워커의 대기 방향을 설명합니다.
4. 각 보고서의 원본 링크를 한 번씩 눌러 어디에 증거가 있는지 확인합니다.
5. 모르는 질문에는 확인한 근거와 미확인 범위를 말하는 연습을 합니다.

대본을 그대로 외워 이미 이해했다고 주장할 필요는 없습니다. “Codex의 도움으로 절차를 구성했고, 직접 실행한 결과를 대조하면서 이 근거로 판단했습니다”라고 작업 범위를 사실대로 설명합니다.
