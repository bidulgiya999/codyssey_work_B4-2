# 평가 때 화면을 보며 설명하는 순서

평가자가 보는 항목별 답변과 운영 응용 질문은 [평가 항목1~4·개념 해설](evaluation-rubric-guide.md)을 확인하세요. 장애별 예상 질문은 [총48개 질문·답변](evaluation-qa.md)에 있습니다.

문장 아래에 답변과 이유를 붙여 연습하려면 [발표 메모·OOM·CPU·Deadlock 질문답변](evaluation-qa.md)을 함께 읽으세요. [메모장용 파일](evaluation-qa.txt)도 제공합니다.

기준: **2026-11-10 실제 실습**, 작업 위치: **plus_2026_11_10/**. 이번 필수 실험6회, 보고서3건, 증거 백업과 GitHub 업로드는 완료했습니다. 남은 준비는 본인 설명 연습과 평가·제출 절차 확인입니다.

관제 코드·절차·보고서 정리에는 Codex의 도움을 받았고, 사용자가 Ubuntu에서 직접 명령을 실행하며 실제 출력을 확인했습니다. 도움받은 범위와 직접 확인한 내용을 사실대로 설명합니다.

## 1. 먼저 열어둘 화면

다음 다섯 화면을 순서대로 엽니다. 모든 원본 파일을 처음부터 끝까지 읽을 필요는 없습니다. 먼저 보고서 안의 실제 출력 발췌를 보여주고, 질문받으면 원본 링크로 이동합니다.

| 순서 | 열 화면 | 가리킬 부분 | 설명할 내용 |
|---|---|---|---|
| 1 | [이번 실습 README](README.md) | 보고서3건 요약 | 과제 목적과 비교 실험 전체 |
| 2 | [관제 코드](scripts/monitor.sh) | ps 조회·반복·CSV 출력 | 어떤 데이터를 어떻게 기록했는지 |
| 3 | [OOM 보고서](reports/01-oom.md) | 비교 표 → RSS → 종료 로그 → 조치 | 메모리 증가와 보호 종료, 임시 조치 |
| 4 | [CPU 보고서](reports/02-cpu.md) | 비교 표 → Watchdog → 냉각 →70% 화면 | 보호 종료와 진행 확인, 지표 구분 |
| 5 | [Deadlock 보고서](reports/03-deadlock.md) | 비교 표 → 자원 대기 → After 로그 | 살아 있지만 정체된 상태와 회피 |

전체 발표는 약7~10분을 기준으로 연습합니다. 평가 시간이 더 짧으면 각 보고서의 마지막 “평가 설명 문장”을 중심으로 말합니다. 실제 평가 시간과 형식은 평가자의 안내를 따릅니다.

## 2. 시작: 과제 목적과 관제 방법

### 화면에서 볼 곳

[README](README.md)의 “평가 준비와 보고서”, 필요하면 [환경 정보](environment-at-backup.txt)와 [monitor.sh](scripts/monitor.sh)를 엽니다.

### 말할 문장

> 이 과제는 Linux 프로그램의 메모리 문제, CPU 과점유, 교착상태를 로그와 관제 데이터로 분석하는 실습입니다. 각 장애에서 설정 변경 전후를 비교하고, 현상·증거·원인 판단·조치와 검증을 보고서로 정리했습니다.
>
> Ubuntu WSL2에서 일반 사용자로 실행했습니다. 부모 실행기와 작업 자식 PID를 구분했고, monitor.sh로 약1초마다 자원 상태를 기록했습니다. CPU의 짧은 상승은 top을0.1초 간격으로 추가 관측했습니다.

### 짧게 알아둘 말

- PID: 실행 중인 프로세스 식별 번호.
- RSS: OS가 보는 실제 RAM 상주 메모리.
- 로그: 앱이 남긴 상태·작업·보호 동작 기록.
- monitor.sh: 지정한 PID를 ps로 조회하고 반복해 CSV로 출력하는 관제 코드.
- 환경변수: 실행할 앱에 전달하는 설정. 파일 저장과 source로 적용하는 일은 구분.

부팅 검사 통과는 실행 준비 조건을 통과했다는 의미입니다. 이후 장애가 없다는 보장은 아닙니다.

## 3. OOM 보고서: 왜 종료됐고 무엇을 바꿨나

### 화면을 이동하는 순서

1. [OOM 보고서](reports/01-oom.md)의 “Description” 비교 표:128/256과 고정 조건을 보여줍니다.
2. “메모리 상승 수치”: RSS가18,392→146,412KiB로 증가한 부분을 가리킵니다.
3. “종료 직전 로그”: Memory limit exceeded와 Self-terminating을 가리킵니다.
4. “Workaround & Verification”:17.185→32.355초와 임시 조치 결론을 보여줍니다.

원본을 물으면 [128MB 앱 로그](evidence/oom-128-20261110-193545/app.log)나 [관제 CSV](evidence/oom-128-20261110-193545/monitor-11373.csv)를 엽니다.

### 이어서 말할 문장

> 앱 실행 후 메모리 사용량이 증가하다 종료됐습니다. 메모리 한도를128에서256MB로 바꾸고 CPU 설정100과 동시 설정false는 유지했습니다.
>
> RSS 증가를 관측했고, MemoryGuard가 한도 초과와 해당 PID의 자체 종료를 기록했습니다. 따라서 직접적인 종료 원인은 앱의 메모리 보호 정책으로 판단했습니다.
>
> 한도를 높이자 생존 시간이17.185초에서32.355초로15.170초 늘었습니다. 그러나 같은 보호 종료가 반복됐으므로 한도 상향은 종료를 지연한 임시 조치였습니다.

### 왜 임시 조치인가

바꾼 명령은 export MEMORY_LIMIT=256입니다. 메모리가 증가하는 내부 코드를 고친 것이 아니라 앱에 전달하는 보호 한도를 높였습니다. 누적은 계속됐습니다. 물이 계속 차는 상황에서 “여기까지 차면 멈춘다”는 기준선을 높인 것과 같습니다.

128을 정확히 찍지 않고150MB,256은275MB에서 초과한 이유는 앱 로그의 증가 단계가25MB였기 때문입니다. RSS와 내부Heap은 다른 지표입니다. 종료 코드137만으로 커널OOM Killer가 개입했다고 말하지 않습니다.

## 4. CPU 보고서: 무엇이 개선됐고 무엇은 주장할 수 없나

### 화면을 이동하는 순서

1. [CPU 보고서](reports/02-cpu.md)의 비교 표:80→40만 변경했고 다른 설정은512/false로 고정했음을 보여줍니다.
2. “Before: CPU 상승과 Watchdog 종료”: 임계치 위반과 SIGTERM 문구를 가리킵니다.
3. “After: 냉각과 생존”: 냉각 로그와 ELAPSED86의 ps 행을 가리킵니다.
4. “예상과 달랐던70% 구간”: 실제 작업 PID13127의 %CPU70.0을 보여줍니다.
5. “Workaround & Verification”: 수동 종료 기록과 조치의 한계를 보여줍니다.

원본을 물으면 [CPU80 앱 로그](evidence/cpu-80-pty-20261110-194141/app.log), [CPU40의70% 화면](evidence/cpu-40-pty-20261110-194524/top-high-frames.txt), [수동 정리 기록](evidence/cpu-40-pty-20261110-194524/cleanup.log)을 엽니다.

### 이어서 말할 문장

> CPU 설정80에서는 부하가 증가하다 CPU Threshold Violated와 Watchdog의 SIGTERM 종료 요청이 기록됐습니다. 따라서 과점유 방지 정책에 따른 보호 종료로 판단했습니다.
>
> CPU 설정만40으로 낮춘 뒤에는40%에서 냉각하는 앱 로그와 경과86초 시점의 생존·작업 진행을 확인했습니다. 이후 실험자가 수동 종료했습니다.
>
> 다만 변경 후 top의 관측 최대는70%였습니다. 앱 설정값과 내부 부하, OS의 프로세스 전체 구간 사용률을 구분했으며, 전체 CPU가40% 이하로 제한되거나 최대값이 낮아졌다고 주장하지 않았습니다.

### 가장 중요한 구분

| 항목 | 뜻 |
|---|---|
| CPU_MAX_OCCUPY=40 | 앱에 전달한 설정값 |
| 앱 Current Load | 앱 내부 계산·기록 지표. 정확한 계산식은 미확인 |
| ps %CPU | 프로세스 실행 이후 누적 평균 |
| top %CPU | 프로세스 전체의 갱신 구간 사용률 |

앱의 냉각·생존은 확인했습니다. OS 최대는50→70%였고 관측 기간도 다르므로 전체 부하 개선을 최대값 하나로 판정하지 않습니다.70%가 특정 메모리 작업 때문인지 작업별 기여도까지는 확인하지 않았습니다.

### 두 실행이143이어도 다른 이유

143은 SIGTERM 해석과 일치하는 종료 상태입니다. 누가 요청했는지는 숫자만으로 알 수 없습니다. CPU80에는 Watchdog 문장이 있고 CPU40에는 실험자의 manual SIGTERM 기록이 있습니다. 이 두 파일을 대조해 구분했습니다.

## 5. Deadlock 보고서: 왜 살아 있어도 정상 진행은 아닌가

### 화면을 이동하는 순서

1. [Deadlock 보고서](reports/03-deadlock.md)의 비교 표: true/false 두 관측 결과를 보여줍니다.
2. “Before: PID 유지와 정체”: PID15052가 유지되지만 로그2802바이트·RSS18428KiB가 그대로인 점을 가리킵니다.
3. “마지막 로그의 자원 보유와 추가 요청”: T1의A보유/B대기와 T2의B보유/A대기를 보여줍니다.
4. “After: 진행과 메모리 정리”: 로그8778→9439바이트와 작업 진행을 가리킵니다.
5. “Workaround & Verification”: 관측 구간의 회피라는 결론과 수동 정리를 보여줍니다.

원본을 물으면 [true 스냅샷1](evidence/deadlock-true-20261110-195228/snapshot-1.txt), [스냅샷2](evidence/deadlock-true-20261110-195228/snapshot-2.txt), [false 스냅샷1](evidence/deadlock-false-20261110-195628/snapshot-1.txt), [스냅샷2](evidence/deadlock-false-20261110-195628/snapshot-2.txt)를 엽니다.

### 이어서 말할 문장

> true에서는 PID는 남아 있지만10초 간격 두 관측에서 RSS와 로그가 정체됐습니다. 첫 워커는A를 가진 채B를, 두 번째는B를 가진 채A를 기다려 순환 대기가 만들어졌습니다.
>
> 동시 설정만false로 변경하자 같은10초 비교에서 로그가661바이트 늘고 CPU 냉각과 메모리 정리 등 작업이 진행했습니다. 따라서 관측 구간에서 해당 교착 경로가 회피됐다고 판단했습니다.
>
> 두 실행은 증거 수집 후 수동 종료했습니다. false에서도 스레드3개와 메인 대기가 남았으므로, 전체 단일 스레드 전환으로 설명하지 않았습니다.

### 그림으로 이해하기

```text
워커1: A를 보유 → B가 필요함 ─┐
                           │ 서로가 가진 자원을 기다림
워커2: B를 보유 → A가 필요함 ─┘
```

futex_do_wait는 동기화 대기 위치이며 정상 대기도 가능합니다. 교착은 이 한 항목으로 확정한 것이 아니라 보유·추가 요청 관계와 반복 관측의 정체를 함께 봤습니다.

교착4조건은 상호 배제, 점유 대기, 비선점, 순환 대기입니다. 실제 락 종류와 타임아웃 코드는 확인하지 않았습니다. 근본 수정으로 락 획득 순서를A→B처럼 통일하는 방안을 제안할 수 있습니다.

## 6. 마지막 정리 발언

화면은 [실습 README](README.md)로 돌아옵니다.

> 이번 실습에서는 사용률 하나나 PID 존재만으로 정상 여부를 판단하지 않고, 설정·관제 데이터·앱 로그를 연결해 원인을 판단했습니다. 설정 변경으로 확인된 효과와 확인하지 못한 범위를 구분했고, 원본 증거와 수동 종료 기록을 보존했습니다.

확인하지 못한 질문에는 다음처럼 답합니다.

> 그 부분은 이번 자료로 확인하지 못했습니다. 제가 확인한 증거는 여기까지이고, 정확한 판단에는 추가 분석이 필요합니다.

예를 들어 정확한 누수 코드 위치는 소스 분석이, 작업별 CPU 기여도는 프로파일링이, 실제 응답 지연 개선은 별도 부하·지연 측정이 필요합니다.

## 7. 평가 직전 체크

- 보고서가 기존10월9일 자료가 아닌 **plus_2026_11_10의 이번 실습**인지 확인합니다.
- OOM은 “한도 상향으로 지연됐지만 같은 종료 반복”을 설명합니다.
- CPU는 “냉각·생존 확인, top70%도 보존, 지표 구분”을 설명합니다.
- Deadlock은 “PID 유지+정체+순환 대기, false에서 진행”을 설명합니다.
- 자동 보호 종료와 실험자의 수동 종료를 구분합니다.
- 숫자를 전부 외우기보다 표와 로그에서 근거를 찾아 보여주는 연습을 합니다.
- 학교·평가자가 요구한 제출 링크와 기한, 실제 평가 형식을 마지막으로 확인합니다.
