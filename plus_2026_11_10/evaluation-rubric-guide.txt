장애별 예상 질문48개 (evaluation-qa.md)와 함께 읽습니다. 항목1은 산출물·증거, 항목2는 도구 이해, 항목3은 원리·판단, 항목4는 운영 응용·개선 제안을 확인하는 구조입니다. 본 문서의 대응표는 증거 위치를 안내하며 평가 점수를 대신 판정하지 않습니다.

2. 항목2: 어떤 명령과 옵션을 왜 썼는가

2-1. monitor.sh의 메모리 추적·추출 방법

- 질문: 메모리 증가를 추적한 명령과 데이터 추출을 구체적으로 설명하세요.
- 답변: ps -p로대상 PID만조회하고 -o로pid·ppid·etimes·pcpu·pmem·rss·nlwp·stat열을골랐습니다. 각필드뒤의=로제목을숨겼고, awk로8열상태가Z로시작하는행을제외한뒤쉼표로연결했습니다. date로시각을붙이고sleep1로반복했습니다.
- 왜 이렇게 했는지: 실제작업자식의상주메모리변화를같은 형식으로계속기록하기위해서입니다. 단순MEM%보다KiB단위RSS로크기변화를명확히확인했습니다.
- 쉬운 설명: ps가값을가져오고awk가표를정리하고sleep이다음관측까지기다립니다.
- 참조: 실제 monitor.sh (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/scripts/monitor.sh), OOM128 CSV (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/oom-128-20261110-193545/monitor-11373.csv); 정확한ps열의의미는 ps 매뉴얼 (https://man7.org/linux/man-pages/man1/ps.1.html).

실제 코드의 핵심 구문입니다. 이미 설정한pid와Bash를전제로한해설이며독립실행용블록은아닙니다.

ps -p "$pid"   -o pid=,ppid=,etimes=,pcpu=,pmem=,rss=,nlwp=,stat=   2>/dev/null |
  awk '$8 !~ /^Z/ {
      printf "%s,%s,%s,%s,%s,%s,%s,%s",           $1,$2,$3,$4,$5,$6,$7,$8
  }'

| 구문 | 뜻 |
|---|---|
| -p | 특정PID조회 |
| -o | 필요한 열·순서지정 |
| rss | 실제상주량,KiB |
| pmem | 물리메모리대비RSS비율 |
| awk의$1~$8 | ps출력의필드. 셸인자$1과구분 |
| !~ /^Z/ | 좀비상태행을제외 |
| date -Iseconds | 관측 시각·시간대 표시 |
| sleep1 | 반복사이대기.조회시간도있어정확한고정1초는아님 |

현재스크립트는ps표준 오류를버려행이없으면종료합니다. 실제종료·좀비제외·조회 실패를엄격하게구분하지못하는한계가있어원인로그와대조했습니다.

2-2. CPU 도구·옵션 구분

- 질문: CPU 사용률 도구를 왜 골랐고 옵션은 무슨 뜻인가요?
- 답변: ps누적 평균과top 구간 사용률을함께확인했습니다. 짧은상승을보려고top -b -d0.1 -w180 -p PID목록으로기록했고첫프레임은제외했습니다.
- 왜 이렇게 했는지: 전체 수명평균은짧은변화를희석할수있고대상 PID별 수치를확인해야하기때문입니다.
- 쉬운 설명: 평균속도계와짧은구간속도계를함께본것입니다.
- 참조: CPU 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/02-cpu.md)의수집명령·비교 표, top 매뉴얼 (https://man7.org/linux/man-pages/man1/top.1.html).

| 옵션·도구 | 이번에 사용한 목적 |
|---|---|
| LC_ALL=C | 출력언어·소수점형식통일 |
| top -b | 배치텍스트출력 |
| -d0.1 | 약0.1초갱신간격 |
| -w180 | 출력폭지정 |
| -p PID목록 | 대상앱으로관제범위제한 |
| ps -o pcpu | 프로세스수명기준CPU평균 |
| script -q -e -f -c | PTY실행기록·종료 상태반영·기록반영·명령지정 |
| top -H / ps -L | 스레드별보기.이번Deadlock실측에는ps -L사용 |

일반적인top기본Irix표시에서프로세스100%는논리CPU하나기준입니다. 시스템요약%Cpu(s),프로세스%CPU,앱 내부Current Load는구분합니다. 열설정이바뀌면awk의$9파싱도재확인해야합니다.

2-3. 살아 있지만 멈춘 상태의 판단 순서

- 질문: 어떤 도구를 어떤 순서로 써서 정체를 판단했나요?
- 답변: 먼저ps -ef로PID와부모 관계를확인하고,monitor시계열과ps -L로자원·스레드 상태를봤습니다. stat과tail로로그 크기·수정 시각·마지막 문장을확인한뒤10초간격으로반복했습니다. 마지막으로락보유와추가 요청의순환관계를연결했습니다.
- 왜 이렇게 했는지: PID가없는종료와PID가남은정체를구분하고, 정상 대기와교착을구분하기위해서입니다.
- 쉬운 설명: 존재확인→상태확인→시간이지나도진행하는지확인→기다리는이유추적입니다.
- 참조: Deadlock 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/03-deadlock.md), true 스냅샷1 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-true-20261110-195228/snapshot-1.txt), true 스냅샷2 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-true-20261110-195228/snapshot-2.txt), true 대기 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-true-20261110-195228/app.log).

도구순서는관찰목적에따른판단흐름입니다. 모든장애에서반드시같은 명령순서여야하는규칙은아니며, 긴급한자원 고갈이면보호조치와짧은증거수집을병행합니다.

3. 항목3: 보호 정책과 교착 원리를 설명할 수 있는가

3-1. MemoryGuard는 왜 프로세스를 종료하나요?

- 답변: 메모리가계속누적되면다른작업이쓸물리메모리가줄고페이지회수·스왑등으로영향이번질수있습니다. 앱이설정한보호기준을넘은프로세스를종료해영향을제한하는정책입니다.
- 왜 이렇게 했는지: 한프로세스의문제가전체시스템불안정으로번지는것을줄이려는보호동작으로로그에기록됐기때문입니다.
- 쉬운 설명: 한호실의과부하를차단해건물전체의부담을줄이는비유입니다.
- 참조: OOM 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/01-oom.md)의원인 분석, OOM128 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/oom-128-20261110-193545/app.log)의to prevent system instability문장.
- 한계: 이번엔커널OOM Killer나실제시스템전체RAM고갈을입증한것은아닙니다. 종료에는미완료작업손실가능성도있어운영에서는영향을고려합니다.

3-2. CPU 과점유 시 왜 단일 프로세스를 종료할 수 있나요?

- 답변: 과점유프로세스가CPU실행시간을경쟁하면다른작업의대기와응답지연을늘릴수있습니다. 해당프로세스의부하를제거해다른작업의자원을확보하려는보호조치입니다.
- 왜 이렇게 했는지: 이번 앱에서는Watchdog가SIGTERM을명시했습니다. 운영에서는상황에따라부하제한·트래픽조절·자원격리도검토해야합니다.
- 쉬운 설명: 공용자원을독점한한작업의부하를줄여다른작업이진행할여지를만드는것입니다.
- 참조: CPU 80 종료 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/cpu-80-pty-20261110-194141/app.log), CPU 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/02-cpu.md).
- 한계: 프로세스종료가항상첫대응이거나모든시스템을안전하게만드는것은아닙니다. 이번에는 실제응답지연개선까지측정하지않았습니다.

3-3. 상호 배제와 순환 대기로 Deadlock을 설명하세요

- 답변: 자원을동시에여럿이소유할수없는상호 배제조건에서,T1이A를보유한채B를,T2가B를보유한채A를기다리면대기 관계가고리가됩니다. 보유·대기와락을회수하지못하는조건아래진행하지못합니다.
- 왜 이렇게 했는지: 단순CPU저하보다자원의소유·요청관계를설명하는것이교착원인을보여주기때문입니다.
- 쉬운 설명: 서로한쪽열쇠를쥐고상대열쇠를기다리는것입니다.
- 참조: Deadlock 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/03-deadlock.md)의교착조건표, true 대기 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-true-20261110-195228/app.log); 원리참고 OSTEP 동시성 문제 (https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf).

교착4조건은고전적인재사용자원모델의필요조건으로설명합니다. 조건들이성립할수있다는말만으로현재교착을자동확정하지않고실제대기 관계와진행정체를확인합니다. 이번비선점은로그와일반락모델로해석했으며내부락 종류를확인한것은아닙니다.

3-4. 로그에서 순환 의존 관계를 어떻게 추적했나요?

- 답변: 각워커의LOCK ACQUIRED를먼저찾아소유자원을표에적고,같은워커의Need resource와WAITING을찾아추가 요청을적었습니다. T1은A소유/B요청,T2는B소유/A요청이므로고리가만들어집니다.
- 왜 이렇게 했는지: WAITING문구의개수보다어떤소유관계때문에막혔는지가원인 분석의핵심이기때문입니다.
- 쉬운 설명: ‘누가무엇을가지고누구것을기다리나’를두줄로정리합니다.
- 참조: true 대기 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-true-20261110-195228/app.log)와 Deadlock 보고서 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/reports/03-deadlock.md)의자원 보유·추가 요청발췌.

T1 ── 기다림 ──> B (T2 보유)
T2 ── 기다림 ──> A (T1 보유)

4. 항목4: 실제 운영이라면 어떻게 개선할 것인가

이 절은 추가 제안과 판단 문제에 대한 답변 예시입니다. 아래 내용을 이번 실습에서 구현·검증한 것으로 말하지 않습니다.

4-1. 메모리 장애를 미리 탐지하도록 monitor.sh를 개선한다면?

- 답변: 시각과RSS를 지속 저장하고 최근 구간의 증가율, 일정 시간 지속 상승, 메모리 예산 접근을 함께 경고하겠습니다. PID와 시작 시각을 함께 기록해PID 재사용을 구분하고 조회 실패를 정상 종료와 분리하겠습니다. 단순 생존 외에 작업 진행도 감시하겠습니다.
- 왜 이렇게 하는지: 보호 종료 뒤에만 조사하는 대신 사전 경고로 대응 시간을 확보하고, 정상 캐시 회수를 누수로 오진하지 않기 위해서입니다.
- 쉬운 설명: 현재 수치뿐 아니라 “얼마나 빨리, 얼마나 오래 늘었나”를 보고 미리 알리는 것입니다.
- 참조: 실제 monitor.sh (scripts/monitor.sh)의 반복 구조, OOM CSV (evidence/oom-128-20261110-193545/monitor-11373.csv)의 시계열.
- 수행 상태: 미구현 제안입니다. 이번 수집기는 경고 전송·추세 판정을 구현하지 않았습니다.

구체적으로 다음을 설계하겠습니다.

1. 증가율은 `(RSS_now - RSS_old) / (관측 시각_now - 관측 시각_old)`로 계산하고KiB/s처럼 단위를 표시합니다. sleep 횟수 대신 실제 경과 시간을 사용합니다.
2. 연속 상승 기간과 사용량을 함께 봅니다. 정상 캐시 회수·기동 직후 할당·짧은 급증을 구분하고, 경고 중복 억제와 해제 조건을 둡니다.
3. 임계치는 같은 범위의 지표에 설정합니다. 앱Heap 한도와OS RSS는 범위가 달라 단순히 빼서 “종료까지 몇 초”라고 계산하지 않습니다. RSS에는 운영상 정한RSS 예산, 앱 내부 값에는 앱 기준을 적용합니다.
4. CPU 구간 값·가용RAM·스왑·컨테이너 사용량과 작업 완료 수·마지막 성공 시각을 함께 봅니다. 작은RSS와 낮은CPU라도 교착 경고가 필요할 수 있습니다.
5. 에러 출력과 표본 누락을 기록합니다. 파일 로테이션·보관 기간·저장 용량·감시 비용·외부 알림도 설계합니다.
6. 정상 증가·회수·프로세스 재시작·조회 실패·교착 시나리오로 경고 정확도를 검증합니다.

자원 격리를 구현한다면 cgroup 제어와 앱 환경변수는 별개입니다. Linux cgroup v2 문서 (https://docs.kernel.org/admin-guide/cgroup-v2.html)의CPU·메모리 제어는 운영 개선 대안이며 이번에 설정한 것은 아닙니다.

4-2. 세 장애 중 가장 치명적인 것은 무엇이라고 생각하나요?

- 답변 예시: 정상적으로 재시작할 수 있는 단일 앱을 가정하면 저는Deadlock이 특히 위험하다고 봅니다. PID가 살아 있어 단순 생존 감시를 통과하면서 요청이 쌓이고, 타임아웃·재시도가 다른 서비스로 번질 수 있기 때문입니다. 락 순서 통일과 작업 진행 감시, 요청 기한·부하 제한으로 예방하겠습니다.
- 왜 이렇게 판단했는지: “조용한 진행 정체”가 탐지·복구를 늦출 수 있다는 서비스 맥락을 근거로 제시한 것입니다.
- 쉬운 설명: 불은 켜져 있는데 업무가 처리되지 않아 줄이 계속 길어지는 상황입니다.
- 참조: Deadlock 보고서 (reports/03-deadlock.md)의PID 유지·로그 정체와 순환 대기.
- 한계: 절대 순위가 아닙니다. 호스트 전체 메모리를 고갈시키는OOM, 실시간 핵심 작업을 지연시키는CPU 과점유가 더 치명적일 수 있습니다. 영향 범위·고객 영향·데이터 손실·복구 시간으로 판단합니다.

4-3. OOM과 Deadlock이 동시에 발생하면 어떤 순서로 대응하나요?

- 답변: 먼저 같은PID인지 다른 프로세스인지, 호스트·컨테이너 메모리 여유와 고객 영향을 빠르게 확인합니다. 짧은 로그·설정·PID/스레드 상태를 보존하면서 새 트래픽과 동시성을 줄이고, 호스트 고갈이 임박했다면 메모리 위험 격리·복구를 우선하겠습니다. 안정화 후 교착의 소유·대기 관계를 추적하겠습니다.
- 왜 이렇게 하는지: 증거를 무한정 모으다 전체 장애를 키워서는 안 되며, 즉각적인 큰 위험을 먼저 줄여야 하기 때문입니다.
- 쉬운 설명: 사진은 빠르게 남기되 건물 전체가 위험하면 불부터 막고, 이후 어디서 무엇이 막혔는지 조사합니다.
- 참조: OOM 보고서 (reports/01-oom.md)의 시스템 영향, Deadlock 보고서 (reports/03-deadlock.md)의 스레드·대기 근거.
- 조건부 판단: 메모리는 안정적이고 교착이 핵심 거래 전체를 막는다면 교착 서비스의 트래픽 우회·복구가 우선일 수 있습니다. 순서는 고정 정답이 아니라 실제 영향도에 따라 설명합니다.
- 수행 상태: 동시 복합 장애 대응을 이번 실습에서 실행한 것은 아닙니다.

실제 대응은 권한·운영 절차에 따라 건강한 인스턴스로 우회하고, 가능하면 배출·정상 종료를 시도합니다. 긴급한 강제 종료는 미완료 작업 손실을 고려해 판단하며 일괄 재부팅부터 하지 않습니다.

4-4. 소스를 수정할 수 있다면 각 장애를 어떻게 개선하나요?

| 장애 | 코드 개선 제안 | 효과 확인 방법 |
|---|---|---|
| 메모리 | 무한 보관 리스트·캐시에 상한/만료/제거 정책, 불필요한 참조 회수, 파일·소켓 닫기, 할당 추적 | 같은 작업량에서 사용량 유지·회수와 기능 정합성 |
| CPU | 비효율 알고리즘·바쁜 대기 제거, 배치 크기·동시성·대기열 상한과 역압, 프로파일링 | 같은 기간·부하에서CPU와 처리량·실제 지연을 함께 비교 |
| Deadlock | 전 경로의 락 순서 통일, 중첩 락 축소, 예외 시 해제, 타임아웃 후 안전한 롤백 | 반복 동시 실행·실패 주입에서 진행성과 데이터 일관성 |

- 답변: 한도를 높이는 대신 자원 누적과 불필요한CPU 작업, 순환 대기를 만드는 코드를 수정하고 같은 조건으로 검증하겠습니다.
- 왜 이렇게 하는지: 직접적인 종료·정체 원인과 그 원인을 만드는 작업 구조를 나누어 다루기 위해서입니다.
- 쉬운 설명: 경고 기준만 바꾸는 대신 쌓이는 원인·독점하는 원인·서로 막는 규칙을 고치는 것입니다.
- 참조: 각 보고서의 추가 제안. Python 소스 접근이 가능하면 tracemalloc (https://docs.python.org/3/library/tracemalloc.html)으로 할당을 추적하고 threading (https://docs.python.org/3/library/threading.html)의 락 타임아웃·컨텍스트 관리도 검토할 수 있습니다.
- 수행 상태: 소스 수정은 미수행입니다. 제공 바이너리의 내부 구현을 해독하지 않았습니다.

캐시 상한은 functools의LRU 캐시 (https://docs.python.org/3/library/functools.html#functools.lru_cache) 같은 방법을 참고할 수 있습니다. TTL은 별도 정책이 필요하며 lru_cache 자체가 자동TTL을 제공한다고 말하지 않습니다. Python 참조를 제거해도OS RSS가 즉시 같은 만큼 내려간다고 보장하지 않습니다. 타임아웃은 롤백·해제와 함께 설계하고, 무한 재시도로 새 문제를 만들지 않도록 합니다.

4-5. 처음부터 다시 한다면 무엇을 다르게 하나요?

- 답변: 실행 조건과 증거 이름을 먼저 고정하고, PID뿐 아니라 시작 시각·앱/도구 버전·수집 범위를 남기겠습니다. 앱과 관제를 함께 시작하고CPU 최대 비교는 기간과 부하를 맞추겠습니다. 처음부터 생존·응답·작업 진행을 분리해 확인하겠습니다.
- 왜 이렇게 하는지: 표본 차이·출력 버퍼링·PID 혼동·종료 원인 혼동 때문에 결론이 과장되는 것을 줄이기 위해서입니다.
- 쉬운 설명: 실험 노트의 조건·시각·단위를 먼저 맞추면 나중에 설명하기 쉽습니다.
- 참조: CPU 보고서 (reports/02-cpu.md)의359/1462표본 차이와70% 구간, monitor.sh (scripts/monitor.sh)의 현재 한계, 각cleanup.log.
- 실제 배운 점: 이번에도70%를 기대한40으로 바꾸지 않고 원본 화면과 주변 로그를 대조했습니다. 이후 같은 기간의 비교·작업별 분석을 추가하면 더 명확해집니다.

5. 핵심 개념을 쉽게 설명하고 이번 증거와 연결하기

5-1. 메모리 누수와 OOM

- 개념: 더 이상 필요 없는 메모리를 반환·회수하지 못하거나 불필요한 참조·보관이 누적되는 문제입니다. OOM은 필요한 메모리를 확보하지 못하는 상황입니다.
- 비유: 물컵을 비우지 않고 계속 따르면 한계에 닿습니다.
- 이번 연결: RSS와 내부 Heap 증가 후 앱 MemoryGuard가 종료했습니다. 특정 누수 코드 위치나 커널 전체 OOM을 입증한 것은 아닙니다.
- 주의: 누수가 모든 OOM의 유일한 원인은 아니며 모든 증가가 누수도 아닙니다. 정상 캐시는 회수될 수 있습니다.

5-2. MemoryGuard

- 개념: 앱 내부에서 메모리 기준을 확인하고 보호 동작을 하는 정책입니다.
- 비유: 과부하가 난 호실을 차단해 건물 전체의 영향을 줄이는 것입니다.
- 이번 연결: Memory limit exceeded와 Self-terminating이 직접 증거입니다. 137은 SIGKILL 해석과 일치하지만 커널 OOM 주체의 단독 증거는 아닙니다.
- 주의: MEMORY_LIMIT은 앱 설정이며 OS RSS 전체를 정확히 그 값 이하로 제한하는 명령은 아닙니다.

5-3. CPU 과점유와 Watchdog

- 개념: 실행 시간 경쟁으로 다른 작업에 영향을 줄 수 있는 과도한 CPU 작업과 이를 감시하는 보호 동작입니다.
- 비유: 공용 자원을 독점한 작업을 감시자가 중단시키는 것입니다.
- 이번 연결: 내부 50.50%에서 위반·SIGTERM, 40 설정에서 냉각·진행을 봤습니다.
- 주의: CPU_MAX_OCCUPY=80이 OS 임계치 80%라고 확인되지 않았고, 40 설정의 top 최대는 70%였습니다.

5-4. Deadlock과 네 조건

- 개념: 자원 대기 관계가 순환해 진행하지 못하는 상태입니다.
- 비유: 서로 한 자원을 쥔 채 상대 자원만 기다리는 두 사람입니다.
- 조건: 상호 배제, 점유 대기, 비선점, 순환 대기입니다. 고전 모델에서 조건 하나를 깨는 설계로 교착을 예방할 수 있습니다.
- 이번 연결: T1의 A 보유/B 대기와 T2의 B 보유/A 대기를 추적했습니다.
- 주의: 외나무다리·철학자 비유는 원리 이해용이고 실제 판정은 로그와 진행 정체로 합니다. 조건 목록만 암기해 현재 교착을 확정하지 않습니다.

5-5. 프로세스·스레드와 스레드 조회

- 개념: 프로세스는 실행 중인 프로그램 단위, 스레드는 그 안의 실행 흐름입니다.
- 비유: 회사와 그 안의 직원입니다.
- 이번 연결: ps -L로 같은 PID의 여러 TID와 WCHAN을 확인했습니다. top -H도 스레드별 조회 대안이지만 이번 실측은 ps -L입니다.
- 주의: 같은 프로세스의 반복 RSS를 스레드 수만큼 더하지 않습니다. 스레드는 같은 프로세스의 메모리 공간을 공유합니다. Python threading 문서 (https://docs.python.org/3/library/threading.html).

5-6. ps·top·htop·pstree·kill

| 도구 | 용도 | 이번 수행 여부 |
|---|---|---|
| ps | 프로세스·스레드 상태 스냅샷 | 실제 사용 |
| top | 반복 자원 관측 | CPU 실험 실제 사용 |
| htop | 상호작용식 프로세스 보기 | 사용했다고 주장하지 않음 |
| pstree | 부모·자식 트리 보기 | 대안. 이번에는 ps·pgrep으로 관계 확인 |
| kill | 대상에 시그널 전송 | -TERM으로 수동 정리 |
| stat/tail | 파일 상태·마지막 로그 조회 | Deadlock 실제 사용 |

도구별 목적에 맞춰 존재·자원·스레드·진행을 확인합니다. kill -0은 일반 종료 요청을 보내지 않고 존재·권한 검사에 사용합니다. SIGTERM은 종료 요청이고 SIGKILL은 강제 종료이며, SIGKILL은 프로세스가 잡아 처리할 수 없습니다. signal 매뉴얼 (https://man7.org/linux/man-pages/man7/signal.7.html).

5-12. 스케줄링 보너스

- 개념: FCFS는 먼저 온 작업부터, Round-Robin은 시간 조각을 번갈아, Priority는 우선순위에 따라 작업을 선택하는 모델입니다.
- 서비스 관점: RR은 짧은 첫 응답 기회를 줄 수 있지만 문맥 전환 비용이 있고, FCFS는 단순하지만 긴 작업 뒤의 짧은 작업이 기다릴 수 있습니다. 우선순위 방식은 기아 문제 등을 검토합니다.
- 이번 로그: false 앱 로그에서 A 완료 19:56:57.654 → B 시작 19:56:57.704 → B 완료 19:56:57.907 → C 시작 19:56:57.958 순서입니다. 앱 작업 실행이 FCFS와 유사하다고 추론할 수 있습니다.
- 주의: 과제의 예시 RR 로그를 이번 실측으로 복사하지 않습니다. 작업 로그의 순서만으로 Linux 커널 스케줄러를 FCFS나 RR로 확정할 수 없습니다. 별도 스케줄러 추적은 미수행입니다.
- 참조: 이번 실제 A·B·C 로그 (https://github.com/bidulgiya999/codyssey_work_B4-2/blob/main/plus_2026_11_10/evidence/deadlock-false-20261110-195628/app.log), OSTEP CPU scheduling (https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf).
