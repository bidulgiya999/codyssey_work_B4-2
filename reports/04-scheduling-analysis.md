# [Analysis] 정상 로그에서 관측한 응용 작업 스케줄러의 순차 실행

## 1. 로그 관찰 개요

정상 시나리오의 Scheduler가 작업 목록 `['Thread-A', 'Thread-B', 'Thread-C']`를 등록했습니다. 아래 분석은 응용 작업 로그에 대한 추론이며 Linux 커널 스케줄러 식별이 아닙니다.

## 2. 증거 자료

| 작업 | 시작 | 완료 |
|---|---|---|
| Thread-A | 12:20:46.925 | 12:20:47.127 |
| Thread-B | 12:20:47.178 | 12:20:47.381 |
| Thread-C | 12:20:47.431 | 12:20:47.634 |

각 작업은20→40→60→80→100%로 완료한 뒤 다음 작업이 시작했습니다. 전체 완료는12:20:47.685입니다. [원본](../evidence/cpu-40-pty-20261009-122044/app.log)

## 3. 패턴 분석 및 결론

관측한 배치에서는 등록 순서대로 완료하는 **FCFS형 순차 패턴**이 가장 단순한 설명입니다. 작업 중간의 A/B/C 교대 로그는 없었습니다.

우선순위 정보가 없어 같은 순서를 만드는 Priority 구현을 배제할 수 없고, 작업보다 긴 시간 할당량도 순차 완료처럼 보일 수 있습니다. 따라서 로그 기반 추론이며 OS 알고리즘이나 내부 코드를 확정하지 않습니다. Thread라는 이름과 실제 TID의 일대일 관계도 미확인입니다.

## 4. 장단점과 적용 범위

순차 처리 모델은 구현과 실행 순서 추적이 간단하고 순서가 중요한 배치에 적합합니다. 앞의 긴 작업이 뒤의 짧은 작업을 지연시킬 수 있습니다.

실시간 요청 처리에서는 작업 분할·동시성·공정성·우선순위와 실제 지연 측정이 필요합니다. 이번 결과를 근거로 Linux가 FCFS/Round-Robin/Priority 중 하나로 스레드를 처리한다고 단정하지 않습니다.
